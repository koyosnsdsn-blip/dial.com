### 2.1 No.77：相談内容へのアクセス経路の限定と監査ログ【決定】

7.16は「相談内容へのアクセス（管理者による参照を含む）」を監査ログの重点監視対象と定めている。一方、SupabaseのData API（PostgREST）を用いてクライアントからDBを直接参照する構成では、**SELECTした事実をアプリケーション側で記録できない**。RLSはアクセスを制限する仕組みであり、参照を記録する仕組みではない。

**決定：** 相談内容を保持するテーブル（`cases`、`messages`、`case_summaries`、`emergency_records`、`case_survey_answers`）への参照経路は、例外なくNuxtのサーバールート経由とする。ブラウザからのData API直接アクセスは対象テーブルについて遮断する。当該サーバールートにおいて `audit_logs` への記録を必須とする。

この決定にともない、RLSは「唯一の防御」ではなく「サーバー側の実装ミスを受け止める多層防御の一枚」という位置づけになる。実装時は、サーバールートの権限判定漏れを検知するテストと、RLSポリシーの双方を維持すること。

なお、この決定はNo.5（外部SNS連携）の実現も容易にする。LINE等の外部経由の利用者は `auth.uid()` を持たないが、全アクセスがサーバールートを通る前提であれば、サーバー側で個別に認可ロジックを実装すればよく、Supabase AuthのRLSモデルに無理に当てはめる必要がない。

### 2.2 No.78／79：認証基盤の方式と3系統の分離【決定・9/30改訂】

データモデル設計の `accounts` は `password_hash` 列を持ち、認証を自前で実装する前提となっている。

**決定：** 利用者（`accounts`）および相談員・管理者（`counselors`）はSupabase Authを採用する。`accounts.password_hash` は廃止し、`accounts.account_id` は `auth.users.id` と対応させる。RLSポリシーは `auth.uid()` を起点に `accounts.client_id` へ到達させ、データモデル 0.2 のスコープを実現する。

**【9/30改訂】クライアント管理者（`client_admins`）も、`accounts`/`counselors`と同様にSupabase Authを採用する。** 当初（9/7時点）は自前実装の認証（別テーブル・別セッション）とする方針だったが、以下の理由により方針転換した。

- 自前実装はSupabase Auth標準のMFA・レート制限・パスワードポリシーを再実装することになり、対象人数の少なさに見合わないオーバーエンジニアリングと判断した
- 認証基盤そのものを分けなくても、**アクセス可能なデータの範囲をRLSで限定する**ことで7.6.1の分離の実質は担保できる：`client_admins`に紐づくロールは`cases`・`messages`等の相談内容系テーブルへの参照経路を持たず、事前集計済みのビュー（7.6.3の四半期レポート等）のみを参照できる

- `client_admins.admin_id` を `auth.users.id` に対応させ、`password_hash` 列は持たない
- ログイン・セッション発行はSupabase Authに委ね、自前のCookie・署名鍵は用いない
- パスワードポリシー・試行回数制限（No.75、76）・MFA（No.30）はSupabase Auth側の設定機能をそのまま用いる

**残る確認事項：** 7.6.1の「認証基盤を共有しない」を「ログインで越境できない・データ参照範囲が分離されていること」と読むなら本方式で満たせるが、「基盤そのものが物理的・論理的に別であること」まで求める趣旨であれば厳密には満たさない。自治体委託等の契約でこの点が具体的に問われた場合に改めて対応する（5.1.1のトリガー方式に準じる）。

この方式により、Supabaseプロジェクトを増やさずに認証基盤の分離という要件上の要求を満たせる。No.84（環境分離、単一インスタンス継続）とも整合する。

関連して、以下の既存項目の判断が本項に従属する。

- No.30（クライアント管理者の多要素認証の方式）：【9/30】Supabase Auth標準のTOTP（認証アプリ）を用いる。自前実装はしない
- No.75（認証の試行回数の上限とロックの期間）：【9/30決定・暫定】当面はSupabase Auth標準の接続元IP単位の回数制限のみとする。詳細は第4章 No.75 および 2.10 参照
- No.76（パスワードの最低文字数）：【9/30決定】8文字（3系統共通）
- No.11（既存の基本相談サービスとのアカウント連携）：既存のハッシュ形式によってはSupabase Authへの移行に制約が生じ得る

### 2.3 No.80：定期処理の実行基盤

データモデル 第9章に日次5種、月次1種、四半期1種の処理が定義されている。Vercelは常駐プロセスを持たないため、実行手段の決定を要する。

| 方式 | 適する処理 |
|---|---|
| Supabase `pg_cron` | DB内で完結する処理（猶予期間経過後の物理削除、集計） |
| Vercel Cron Jobs | 通知メールの送信を伴う処理（自動クローズの予告、同意の督促、有効期間満了の予告） |

**猶予期間を経過した本文の物理削除（9.3）は対象件数が事前に読めない。** サーバーレス関数の実行時間上限に抵触する可能性があるため、当該処理の方式は特に留意して決定する。

### 2.4 No.81：添付ファイル・画像の保管先

11.8.2の「別途調達を要するもの」にメール配信・決済代行・動画配信・LLMは挙げられているが、**添付ファイルの保管先が欠落している。** 該当するのは以下である。

| 対象 | データモデル上の列 | 性質 |
|---|---|---|
| 相談の添付ファイル | `attachments.file_ref` | 要配慮個人情報を含み得る |
| クライアントのロゴ画像 | `landing_pages.logo_ref` | 公開情報 |

前者は動画配信サービスやCDNとは別の扱いを要する。Supabase Storage を用いる場合はRLSと同等のアクセス制御設定を、外部サービスを用いる場合は国内保管要件（8.7）との整合を確認する。あわせて、9.3に定める物理削除の対象に添付ファイルの実体を含める手順を定める。

### 2.5 No.82：経緯サマリの一時保持先と生成タイミング

データモデル 3 の注記は、経緯サマリを保持せず「参照時に確定済みの `case_summaries` から都度生成する」と定めている。この記述をそのまま実装した場合、**案件詳細画面を開くたびにLLMを呼び出すこととなり、相談員の待ち時間が生じる。**

同注記が認めている「入力となる案件サマリの集合から算出した値を鍵とした一時保持」について、以下を確定する。

- 保持先（DBのテーブルとするか、別のキャッシュ機構とするか）
- 鍵の算出方法および失効の条件

本項は No.71（経緯サマリの入力とする案件件数の上限）と一体の問題であり、あわせて確定する。

### 2.6 No.83：2系統ドメインの出し分け

8.6.1は一般向けと企業会員向けを単一のアプリケーションで提供すると定めるが、実現方式は記載がない。**No.89の決定により、これはNuxtのミドルウェアによるホスト名判定ではなく、Vercelプロジェクト自体を分けたうえでのドメイン割り当てで実現する。** 相談者側アプリに一般向け・企業会員向けの両ドメインを割り当て、アプリ内部で契約類型に応じた出し分けを行う。

確定すべきは、8.6.1.1に定める「要素自体を設けない」という要件をアプリ内部の出し分けでどう担保するかである。決済に関する表示、機能1への投稿導線、会員区分の表示について、**非表示とするのではなく描画対象から除外する**構成とする必要がある。

### 2.7 No.84：環境分離とテストデータ【決定】

**決定：** 本番・ステージング用にSupabaseプロジェクトを追加することによる分離は、追加費用が生じるため現時点では行わない。Vercel・Supabaseとも単一インスタンスのまま開発を進める。将来、コストが許容できる段階で見直す。

単一インスタンスであることを前提に、以下を最低限の緩和策として実施する。

- **ローカル開発はSupabase CLI＋Dockerのローカル環境を用いる。** 追加費用なく、開発者の手元で完結する環境を作れる。これにより開発中のコードが本番DBに触れる経路をまず一つ塞げる
- **Vercelのプレビュー環境（プルリクエストごとに自動生成）には、サービスロールキーを配置しない。** 接続先は単一インスタンス（本番）にならざるを得ないが、anonキー＋RLS経由でのアクセスに限定し、RLSを迂回できる状態を作らない
- **サービスロールキーはProduction環境変数にのみ置く。** Preview・Developmentのスコープには含めない
- 合成データの生成・投入は、本番と同一インスタンス上で行わざるを得ないため、**本番の相談内容をコピーしての動作確認は行わない**運用ルールを明文化する
- 将来、追加費用を許容してプロジェクトを分離する際の移行手順（スキーマ・RLSポリシーの再現方法）を、着手前に一度整理しておくと切替がしやすい

なお、No.78/79（9/30改訂）により3系統とも同一のSupabase Authを用いるため、本項の単一インスタンス継続と整合している。

### 2.8 No.88：相談者数増大時のスケール手段【決定】

**決定：** 特定の手段に決め打たない。負荷の実態が出た時点で、その時点のボトルネックに応じて以下から選ぶ。現行設計（No.77のサーバールート経由、No.84の単一インスタンス、8.6.1のSSR）は、どの手段を選ぶ場合にも変更を要しない。

| 手段 | 何に効くか |
|---|---|
| Vercel側でのレート制限 | 突発的なアクセス集中・悪意あるリクエスト。No.77で全アクセスがサーバールートを通るため、ミドルウェアの追加のみで対応できる |
| Supabase接続プーラー（Supavisor）でのロール別接続数上限 | 相談者側の接続がDBの接続枠を食い潰す事態 |
| Supabaseのコンピュートスペックの引き上げ | 全体的な処理能力不足。インフラ側の設定変更のみ |
| リードレプリカの追加 | 機能1（Q&A閲覧）のような読み取りが多い処理 |
| Vercelのキャッシュ／ISR | 機能1のようなSSR前提の公開ページ |

**今のうちに意識しておくとよい点：** 機能1（読み取り中心）と機能2（書き込み中心・厳密な整合性が必要）は性質が異なる。DBへの問い合わせを書く際、「これは読み取り専用の処理か」を意識したコードの書き方にしておくと、将来リードレプリカを導入する際に該当箇所を探す手間が減る。今すぐの実装対応は不要で、コーディング時の習慣の話である。

### 2.9 No.89：Vercelアプリの分割範囲【決定・一部未確定】

**決定：** Vercelアプリ（Nuxt）を、相談者側（一般向け・企業会員向け、8.6.1）と管理側（運営の相談員・管理者）で分割する。理由は運用上の可用性ではなく、**セキュリティの被害範囲の限定**である。

- 相談者側は匿名・軽い認証のトラフィックを受け、攻撃対象になりやすい
- 管理側は少人数の相談員・管理者が使い、`緊急フラグ`対応という停止してはならない機能を持つ
- 単一アプリでは、相談者側の脆弱性が同一デプロイ内の管理側の環境変数・コードに到達し得る。分割すればアプリ層はその経路を断てる

**限界：** Supabaseは単一インスタンス（No.84）のままのため、DB接続・CPU・IOの競合はアプリを分けても解消しない。相談者側の負荷がDBを詰まらせれば、管理側のクエリにも影響する。この経路への緩和策はNo.88の接続プーラーでのロール分離を参照

**費用への影響：** Vercelの課金はチームのシート数と使用量（帯域・関数実行数等）が基準であり、プロジェクト数自体には課金されない。No.84のSupabaseプロジェクト分割（DBインスタンス増加分のコストが生じるため見送り）とは事情が異なり、追加費用なく実施できる

**実装方法：** Nuxt LayersまたはCommon packageで共通部分（Supabaseクライアント初期化、共通コンポーネント）を切り出し、2つのNuxtアプリ（2つのVercelプロジェクト）からそれぞれ参照する。環境変数は両プロジェクトに同一の値を設定する

**未確定：** クライアント管理サイト（7.6）をこの2分割のどちらに含めるか、あるいは3つ目のアプリとするかは未確定。クライアント管理者は相談内容系テーブルへの参照経路をRLSで持たず（No.78/79、9/30改訂）、扱うデータも事前集計値のみ（7.6.3）という低リスクな性質のため、さしあたり管理側に含める前提で進めてよいと考えるが、要確認

### 2.10 No.90：認証要件のうちSupabaseの上位プランに依存する機能【9/30判明】

### 2.12 利用者の登録方式の変更：ニックネームとパスワードのみ【9/30 入江さんの指示】

**決定**：相談者側の新規登録は、**ニックネームとパスワードだけ**で行う。メールアドレスは求めない。相談を始めるまでの手数を減らすため。招待コードは登録画面で一緒に入力できる（あとからでも可）。

これは要件定義書 8.4（メールアドレス・パスワードで登録しメール認証を行う）・9.6（本人確認）からの変更であり、**要件定義書の改訂が必要**。

**実装**（相談者側 `utils/nickname.ts`、`server/api/signup.post.ts`）
- Supabase Auth はメールアドレスを前提とするため、ニックネームを正規化（NFKC・小文字化）してハッシュ化し、`u-<ハッシュ>@<ドメイン>` という内部用の識別子を作って登録する。利用者には見せず、メール送信にも使わない
- ドメインは環境変数 `NICKNAME_DOMAIN`（両アプリで同じ値。dev の既定は `dialcom-op-dev.vercel.app`）。Supabase Auth は `.invalid` などの予約済みドメインやDNSに存在しないドメインを拒否するため、DNSに存在しメールを受け取らないドメインを使う。**一度決めたら変えない**（変えると登録済みの利用者がログインできなくなる）。本番では、メールを受け取らない自社のサブドメインを用意する
- 将来メール配信を設定した場合、Supabase の通知メール（パスワード変更の通知など）がこの識別子宛てに送られて不達になる。不達が多いと送信元の評価が下がるため、配信設定の際に、ニックネーム登録の利用者へは送らない構成にすること
- サーバー側で Supabase の管理APIによりユーザーを作成する（確認済みとして作成）。プロジェクト全体の「メールアドレスの確認」の設定は変えていない
- ニックネームは2〜20文字、空白と「@」は不可、重複不可。Auth の user_metadata に保存する
- 自動登録の抑止として、同じ接続元からの登録は1時間に5件まで（仮）。IPアドレスは保存せず、日付を混ぜたハッシュの一部を監査ログに記録する
- 管理側の利用者照会は、ニックネームでも照会できる

**入口を3種類に分けた（10/1 入江さんの指示）**

| 入口 | パス | 登録に必要なもの | 備考 |
|---|---|---|---|
| 招待コードをお持ちの方 | `/start/invite` | ニックネーム・パスワード・招待コード（必須） | コードはアカウント作成の前に確かめる。誤りなら登録しない |
| ニックネームではじめる | `/start/nickname` | ニックネーム・パスワード | 招待コードはログイン後に入力できる |
| メールアドレスではじめる | `/start/email` | メールアドレス・パスワード（確認メールあり） | パスワードの再設定ができる。dev の確認メールは Supabase 組織メンバーのアドレスにしか届かない（No.59） |

どの入口も、同じページで「はじめての方／登録済みの方」を切り替える。トップ（`/`）に3つの入口を並べている。以前の `/login`・`/signup` はニックネームの入口へ転送する。
**どの入口を誰に案内するか（全部を並べて見せるのか、クライアントごとに入口を指定するのか）は未決。**

**この方式で生じる制約と、未決の点**

| 事項 | 現状 | 決めること |
|---|---|---|
| パスワードの再設定（要件 10.3.1） | **できない**。忘れた場合は新しく登録し直す（以前の相談の記録は引き継がれない）。登録画面と「パスワードを忘れた方へ」で明示している | メールアドレスを任意で登録した利用者だけ再設定できるようにするか |
| 返信・終了の通知（要件 10.2） | 送れない。利用者が自分でログインして確認する | 通知を希望する利用者にだけメールアドレスを登録してもらうか |
| 2段階認証（要件 8.8.4・10.3.5） | 未実装。入江さんの意向は「必要な人だけ、メールアドレスで」。要件は認証アプリ（TOTP）を推奨（同居者に見られる懸念があるため、SMSは不可としている） | メールで行う場合、Supabase の標準の多要素認証にはメール方式がないため、自前の実装とメール配信（No.59）の確定が必要。メールも同居者に見られ得る点は SMS と同じ懸念がある |

### 2.13 ホストを1つにまとめた（運営画面を /ops に移した）【10/2 ダイヤルさんの判断】

脆弱性診断の費用が対象のFQDNごとにかかるため、相談者側と管理側の2つのアプリ（2つのFQDN）を、1つのアプリ・1つのFQDNにまとめた。技術基盤設計書 1.2 の「アプリを分けて被害範囲を分離する」方針は、これにより変わる。別チームで動いていたダイヤル.COMの現行仕様も、同じ理由で1つのホスト・パスでの区分にしている。

| 項目 | まとめる前 | まとめた後 |

| 運営画面 | dialcom-admin-dev の `/…` | dialcom-op-dev の `/ops/…`（旧「運営メニュー」は `/ops/menu`） |
| クライアント管理サイト | dialcom-admin-dev の `/portal` | dialcom-op-dev の `/client-admin` |
| 運営画面のサーバールート | `/api/…` | `/api/ops/…`、クライアント管理サイトは `/api/client-admin/…`、定期処理は `/api/cron/…` |
| 運営側のログインの有効時間 | Cookie を8時間で失効 | Cookie は相談者側と共通（12時間）。運営側は「最後に認証した時刻」（アクセストークンの amr）から8時間で打ち切る。画面（`ops/session.ts`）とサーバー（`requireStaff`・`requireClientAdmin`）の両方で検査する |

- ~~運営画面とクライアント管理サイトのログイン画面が共通~~ → 2.14 で分けた（`/ops/login`、`/client-admin/login`）

### 2.14 役割ごとのログインID（同じメールアドレスでも役割が違えば別アカウント）【10/7 ダイヤルさんの判断：案③】

1つのホストにまとめた結果、ブラウザのログイン情報（Cookie）が相談者側・運営側で共通になり、同じメールアドレスで相談者と相談員を兼ねると衝突する懸念が出た。これを避けるため、Supabase Auth に登録する識別子を役割ごとに分けた。

| 役割 | ログインID（Auth 上のメールアドレス） | 入力するもの | ログイン画面 | 本物のメールアドレスの保管先 |
|---|---|---|---|---|
| 相談者（ニックネーム） | `u-<ハッシュ40桁>@内部ドメイン` | ニックネーム | `/start/nickname` ほか入口3種 | なし（任意登録は今後） |
| 相談員・運営管理者 | `s-<ハッシュ40桁>@内部ドメイン` | メールアドレス | `/ops/login`（MFA：`/ops/mfa`） | `counselors.contact_email` |
| クライアント管理者 | `c-<ハッシュ40桁>@内部ドメイン` | メールアドレス | `/client-admin/login`（MFA：`/client-admin/mfa`） | `client_admins.email` |

- ハッシュは、入力を NFKC 正規化・前後の空白除去・小文字化したものの SHA-256 の先頭40桁。計算は `utils/nickname.ts`（ブラウザ・サーバー）と `server/ops/nickname.ts`（サーバー）で同じ。**既存のニックネームのIDは変わらない**（照合テストで確認済み）
- 役割は、Auth 上のメールアドレスの接頭辞とドメインで判定する（`roleOfLoginEmail`）。画面ガード（`ops/guard.ts`）、`requireStaff`、`requireClientAdmin`、`requireAccount` が、それぞれ独立に検査する。接頭辞が違うアカウントは、`counselors` / `client_admins` に行があっても通さない。相談員・クライアント管理者のアカウントは、相談者側を使えない
- 同じメールアドレスで、相談者・相談員・クライアント管理者として別々に登録できる。同じ役割で二重に登録しようとしたときだけ「すでに登録されています」と出す
- ~~同じブラウザでは、ログインは1つだけ（Cookie が共通）~~ → 2.16 で領域ごとにCookieを分けた。同じブラウザで相談者・運営画面・クライアント管理サイトに同時にログインできる

**【暫定】内部ドメインは `dialcom-op-dev.vercel.app` のまま。** 本番ドメインが決まったら、全員分のIDを一括で書き換える（入江さん了承：DBの書き換えは後で行う）。内部ドメインは、①自社が保有し、②固定し、③メールを受け取らない（Null MX と `v=spf1 -all`）ものにすること。ドメインを変える前に、Supabase の認証ユーザー（`auth.users`・`auth.identities`）の識別子を書き換える手順を用意する。本番ドメインを内部ドメインに兼ねる案は、`id.` などの専用サブドメインを使えば成立する（本体側に運営メールの送信設定を置けるため）。

**デプロイ時の一度きりの移行（2026-10-07 実施）**：コードの反映と同時に、既存の相談員2名の Auth 上のメールアドレスを `s-…` に書き換えた（MFA の登録は引き継がれる）。本物のメールアドレスは、マイグレーション `20261007090000_login_id_by_role.sql` で `counselors.contact_email` に写してある。書き換え後は、各自がいったんログインし直す。

残っている検討事項：
- 相談者のメールアドレス登録（任意登録・メールでの入口）は、メール配信の仕組み（No.59）が入ってから、同じ方式（`u-` ＋メールアドレスのハッシュ）に寄せる。いまの「メールアドレスで登録した相談者」は、生のメールアドレスのまま（接頭辞なし）で、相談員・クライアント管理者とは独立している

### 2.15 無償の個人の相談と、企業枠・有料の相談の並行【10/7 ダイヤルさんの指示：C＋D＋切替時の案内】

**きっかけ**：ニックネームで登録して無償の相談を始めた人が、あとから招待コードで企業会員になった。無償の相談が対応中のままだと、企業枠の相談を始められなかった。無償の相談は、相談員の返信がないと（返信待ちの間は自動終了の対象外）長く残る。利用者が自分で終える操作もなかった。下位の権利（無償）が、上位の権利（企業枠・将来の有料）の行使を止めるのは適切でないと判断した。

**決定（仮）**

| 項目 | 内容 | 実装 |
|---|---|---|
| 同時に対応中にできる件数 | **枠ごとに1件まで**（最大2件）。枠は free（無償の個人）と main（企業枠・将来の有料の個人）。無償の相談が対応中でも、企業枠・有料の相談は始められる | `cases.slot`、部分ユニークインデックス `uq_cases_one_open_per_slot`、`user_start_case` |
| 無償の相談の開始 | 何かが対応中のあいだは始められない（無償が2件になる、企業枠と並行して無償を使い続ける、を防ぐ） | `user_start_case` |
| 本人による終了 | 利用者が、対応中の相談を自分で終了できる。終了理由は `user`（相談員の画面には「利用者本人による終了」）。やり取りは終了後も本人が読み返せる | `user_close_case`、`POST /api/cases/[id]/close`、メッセージ画面の「このご相談を終了する」（二段階の確認） |
| 切替時の案内 | 対応中の相談が残ったまま新しい相談を始められるとき（招待コードで所属した直後など）、ご相談ホームと開始画面に案内を出す。「終了して新しく始める」「終了せずに新しく始める」「これまでの相談を開く」の3つ。終了は強制しない（お返事待ちの場合があるため）。会員区分・費用に関する語は使わない（要件 8.6.1.1） | `components/OpenCaseNotice.vue` |
| 相談員側の表示 | 案件詳細に「この相談者は、ほかにも対応中の案件があります」と、案件ID・開始日時・担当を出す。**匿名性とは別の話**：通番（何件目か）は要件 3.4.2 で相談員側にすでに出している。経緯サマリは終了済みの案件だけが対象のため、対応中の別案件は別に示す必要がある | `GET /api/ops/cases/[id]` の `otherOpenCases` |

**要件との差**：要件 3.2.1 は「同時に有効なメッセージボックスは1件まで（付与元を問わず）」。本変更は、その例外。要件定義書の改訂が必要。

**残る論点**

| 論点 | 内容 | 決めること |
|---|---|---|
| 所属前の個人の相談の扱い | 所属後も、過去の個人の相談は個人のまま（クライアントの集計・報告の対象にしない）。付け替えはしない。自治体委託型は、同意前の内容が委託元への報告対象になってしまうため | これでよいか |
| 無償と有料の差 | 無償の個人と有料の個人（5,000円）の差が、費用と有効期間だけになっている（往復も返信の目安も同じ）。無償は回数の制限もない | 有料の個人（決済）を実装するときに、差を設ける |
| 有料の個人の実装時 | 決済の**前**に、main 枠の空きを確認する。課金後に開始できない事態を避ける | 決済実装時 |
| 並行する2件の担当 | 前回の担当を優先して割り当てるため、同じ相談員に2件付く可能性が高い。画面では案件詳細に別案件の表示を出す | 運用で支障があれば、別の相談員への割当を検討 |

### 2.16 認証Cookieを領域ごとに分けた（同じブラウザで同時にログインできる）【10/7 ダイヤルさんの指示】

1つのホストにまとめた（2.13）あと、ログイン情報のCookieが1つだけで、同じブラウザでは相談者・運営画面のどちらか一方にしかログインできなかった。領域ごとに別のCookieを使うようにした。

| 領域 | 画面・API | Cookie 名 | 実装 |
|---|---|---|---|
| 相談者側 | `/…`、`/api/…`（下記以外） | 従来のまま（モジュールの既定） | `@nuxtjs/supabase`（変更なし）。**相談者の再ログインは不要** |
| 運営画面 | `/ops/…`、`/api/ops/…` | `sb-ops-auth-token` | ブラウザ：`ops/authClient.ts`、サーバー：`server/ops/session.ts` |
| クライアント管理サイト | `/client-admin/…`、`/api/client-admin/…` | `sb-client-auth-token` | 同上 |

- サーバーAPIは、**リクエストのパスで読むCookieを決める**。運営のAPIは運営のCookieだけ、クライアント管理のAPIはそのCookieだけ、相談者のAPIは相談者のCookieだけを読む（`utils/authArea.ts`）。別の領域のCookieでは通らない。役割の検査（`s-`/`c-` の接頭辞、MFA（aal2）、認証から8時間、`counselors`/`client_admins` の有効な行）は従来のまま
- 領域ごとにアカウント自体が別（`u-`/`s-`/`c-`、2.14）なので、ログアウトも領域ごと。運営画面でログアウトしても、相談者側のログインは残る
- 招待リンク（`/ops/accept-invite`）は、リンクのトークンに入っているログインIDの接頭辞で、運営用かクライアント管理用かを選んでセッションを保存する
- 相談者側のCookieに、Cookie分離前に入った運営側のアカウントが残っている場合は、相談者側の画面を開いたときにブラウザ側だけ消す（`signOut({ scope: "local" })`）
- Cookie の有効期限は `@supabase/ssr` が固定で長く設定する（400日）。運営側の8時間の上限は、トークンの認証時刻から画面・サーバーが判定する（2.13）。これは従来から変わらない
- **切替時の一度きりの影響**：運営画面・クライアント管理サイトにログイン中の人は、反映後に**1回だけログインし直す**（古いCookieは読まなくなるため）。相談者は影響なし
- 確認：型チェック・ビルド、偽の認証サーバーでの8通りのAPI確認（運営のCookieだけで運営APIが通る、相談者のCookieでは401、クライアント管理のCookieでは運営APIが通らない 等）、ブラウザ（Playwright）で「運営ログインで `sb-ops-auth-token` だけが作られ、相談者側のCookieは残り、運営のログアウトで相談者側は消えない」ことを確認

### 2.17 ニックネームで登録した方の通知用メールアドレス【10/8 ダイヤルさんの判断：A案】

**きっかけ**：ニックネームの方のログインIDは受信できない内部用アドレス（`u-…@内部ドメイン`）。そのため、①新しいお返事のメール通知（10.2）が届かない、②パスワードを忘れても再設定のメールが届かず、運営も本人確認の手段がないため復旧できない（相談履歴に二度と入れない）、という問題があった。

**決定（仮）**：ログインID（ニックネーム）は変えず、通知とパスワード再設定の届け先として、任意でメールアドレスを登録できるようにする（案A。案B＝メール登録への切替は移行の手間が大きい、案C＝画面通知のみは返信に気づけない、として見送り）。

| 項目 | 内容 |
|---|---|
| 保存先 | `account_notify_emails`（`account_id`・`email`・`verified_at`）。ブラウザからは読み書きできない（RLS＋権限なし）。サーバールート `/api/notify-email`（GET/PUT/DELETE）経由。登録・削除は監査ログに残す（メールアドレスは記録しない） |
| 確認 | 登録直後は「確認前」。**確認前のアドレスには、通知もパスワード再設定も送らない**（他人のアドレスの悪用を防ぐ）。確認メールの送信・確認の完了は、メール配信（No.59）の実装後に接続する |
| 画面 | `/mypage/notify-email`（マイページ・お知らせメールの設定から入る）。登録しないとパスワード忘れの際に復旧できないことを明示 |
| 退会 | `accounts.deleted_at` が入ると同時に削除（トリガ） |
| データ出力 | 登録情報に通知用メールアドレス（確認済み／確認前）を含める |
| 実装済み | 保存・表示・変更・削除（`20261008090000_notify_email.sql`、`supabase/tests/notify_email.sql`） |
| 未実装（No.59 待ち） | 確認メール、新しいお返事の通知、パスワード忘れ（ニックネームの方向けの再設定の入口）、パスワード変更の通知 |

**残る論点**
- 同じアドレスを複数のアカウントに登録できる。パスワード再設定に使う段階で、①1アドレス1アカウントに制限する、②再設定のときにアカウントを選ばせる（匿名性との兼ね合い）、のどちらにするか決める
- 再設定の入口（ニックネーム＋確認済みアドレスで再設定）の本人確認の強さ。ニックネームを知られても、確認済みアドレスの受信者でなければ再設定できないようにする
- 未登録の方への働きかけ（初回の相談の前後に登録を案内する）の出し方

### 2.18 IP制限（サイト全体の拒否リスト、クライアント管理サイトの許可リスト）【10/8 ダイヤルさんの指示】

**きっかけ**：攻撃の増加。危険と名指しされた接続元（JPCERT・警察などの公表）を拒否したい。あわせて、要件 8.8.3 のクライアント管理サイトのIP許可リストを実装する。

| 機能 | 内容 | 根拠 | 実装 |
|---|---|---|---|
| ① サイト全体の拒否リスト | 登録した接続元からは、相談者側・運営画面・クライアント管理サイトのすべての画面とAPIを拒否（403）。**許可リストではない**（相談者を職場などに限定しない） | 8.6.4 に反しない範囲での追加 | `server/middleware/ipBlock.ts`、運営メニュー「接続元の拒否リスト」（`/ops/ip-rules`、運営管理者のみ） |
| ② クライアント管理サイトの許可リスト | クライアント単位。1件でも登録があれば、そのクライアントの管理者は登録した接続元からしか管理サイトのAPIを使えない。空なら制限なし。設定は当社のみ（クライアント側からは変更不可）。自治体委託型は設定を推奨と表示 | 8.8.1・8.8.3 | `requireClientAdmin`（`server/ops/portal.ts`）、クライアント設定画面の「クライアント管理サイトのIP許可リスト」 |

- 保存先：`ip_rules`（`kind`＝block／client_admin_allow、`cidr` 型）。ブラウザからは読み書きできない。変更は理由とともに監査ログに残す。`20261008120000_ip_rules.sql`、`supabase/tests/ip_rules.sql`
- 接続元のIPは Vercel が付ける `x-real-ip`（なければ `x-forwarded-for` の先頭）。Vercel はこのヘッダーを上書きするため偽装できない。**Vercel 以外に移すときは見直す**
- 規則はインスタンスごとに30秒キャッシュ。**変更の反映は最大30秒**
- 拒否リストは**複数まとめて登録できる**（10/9。1回50件まで。改行・カンマ・スペース区切り。注意喚起の文書にある `203[.]0[.]113[.]5` の書き方も可。送る前に画面で1件ずつ確認し、1件でも誤りがあれば何も登録しない。登録済みの値は読み飛ばす。監査ログは1回分を1件にまとめて記録）
- 安全装置：自分の接続元を含む値は拒否リストに登録できない／IPv4 は /8、IPv6 は /16 より広い範囲は拒否リストに登録できない／形式の誤り（ホスト部が0でない範囲など）は受け付けない
- 障害時：拒否リストは、DBを読めないときは拒否しない（相談の受付を止めない）。許可リストは、DBを読めない・接続元が分からないときは通さない（業務用のため安全側）
- 許可リスト外からのアクセスは、監査ログ（`client_admin.ip_denied`、接続元IPつき）に残す。不正アクセスの検知に使う

**残る論点**
| 論点 | 内容 |
|---|---|
| Supabase への直接のアクセス | 判定はこのアプリのサーバーで行う。ログインは Supabase Auth に直接行うため、許可リスト外・拒否リストの接続元でも、ログインの試行自体は止められない。クライアント管理者のトークンでは、RLS により事前集計の四半期レポートだけを Supabase から直接読める（このアプリを通らないため、許可リストが効かない）。集計値のみのため影響は小さいが、塞ぐなら「レポートはサーバー経由でのみ読む（ブラウザの直接の権限を外す）」に変える。CLAUDE.md 制約#3 の設計に関わるため、変更前に確認する |
| 運営画面の許可リスト | 要件 8.8.2 は「任意で設定可（必須にしない）」。今回は作っていない。同じ仕組み（`ip_rules` に kind を追加）で作れる |
| 端（エッジ）での遮断 | 静的ファイル（`/_nuxt/…`）はこのアプリを通らないため、拒否リストの対象外（中身は公開情報）。CDN の段階で止める・国単位の制限・回数制限は、Vercel Firewall のカスタムルールで行う（全プランで利用可。件数の上限は Hobby 3件・Pro 40件、IP遮断は Hobby 3件・Pro 100件） |
| 拒否リストの出典と見直し | 公表された接続元は、時間がたつと別の利用者に割り当てられることがある。登録時にメモへ出典と日付を書き、定期的に見直す運用を決める |

### 2.19 公開Q&Aへの「先生コメント」（弁護士・社労士・メンタル相談の先生など）【10/9 ダイヤルさんの構想・仮置き】

**きっかけ**：弁護士ドットコム、アスクドクターズのように、専門家（先生）が質問にコメントをつける機能を入れたい。現在の先生は「メンタル相談の先生」1名のみ。今後、弁護士・社労士など増えても対応できる作りにする。

**決定（仮）**

| 項目 | 内容 |
|---|---|
| 位置づけ | 機能1（公開Q&A）の回答（相談員）に加えて、先生のコメントを載せる層。機能2（個別の相談）とは別。 |
| 質問の割り当て | **カテゴリ（ジャンル）ごとの担当制**（ダイヤルさんの指示）。ジャンルと先生は多対多。質問は、担当ジャンルの先生にだけ見える。担当の先生がいないジャンルは、先生に回さず相談員の回答のみ。先生が複数いるジャンルは、複数の先生がコメントできる。 |
| 先生に見せる質問（仮） | **公開済み（匿名化済み）で、担当ジャンルの質問だけ**。公開前の投稿は見せない（現行の流れは、相談員が確認・回答して公開する1工程で、「確認済みだが未公開」の状態がないため。先生は公開後にコメントを足す形になり、投稿者の同意・匿名化の範囲を広げずに済む）。 |
| コメントの公開前確認（仮） | 先生のコメントは、公開前に相談員が確認する（断定的な表現・個人の特定）。確認待ち→公開、または差し戻し（理由つき）。運用に慣れたら先生の直接公開を検討。 |
| 先生の認証（仮） | 相談員と同じく2段階認証必須（セッションが aal2 のときだけ有効）。 |
| 匿名性（2.6） | 先生に見せるのは使い捨てIDと質問本文のみ。会員ID・過去の投稿・所属先は見せない。 |
| 閲覧範囲（2.4） | 先生コメントも回答と同じマスク規則（未登録・無料会員は冒頭30文字、サーバー側で切り詰め）。 |

| 後回し | 「参考になった」などの評価、利用者から先生への追加質問。 |
