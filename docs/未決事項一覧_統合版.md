### 2.1 No.77：相談内容へのアクセス経路の限定と監査ログ【決定】

7.16は「相談内容へのアクセス（管理者による参照を含む）」を監査ログの重点監視対象と定めている。一方、SupabaseのData API（PostgREST）を用いてクライアントからDBを直接参照する構成では、**SELECTした事実をアプリケーション側で記録できない**。RLSはアクセスを制限する仕組みであり、参照を記録する仕組みではない。

**決定：** 相談内容を保持するテーブル（`cases`、`messages`、`case_summaries`、`emergency_records`、`case_survey_answers`）への参照経路は、例外なくNuxtのサーバールート経由とする。ブラウザからのData API直接アクセスは対象テーブルについて遮断する。当該サーバールートにおいて `audit_logs` への記録を必須とする。

この決定にともない、RLSは「唯一の防御」ではなく「サーバー側の実装ミスを受け止める多層防御の一枚」という位置づけになる。実装時は、サーバールートの権限判定漏れを検知するテストと、RLSポリシーの双方を維持すること。

なお、この決定はNo.5（外部SNS連携）の実現も容易にする。LINE等の外部経由の利用者は `auth.uid()` を持たないが、全アクセスがサーバールートを通る前提であれば、サーバー側で個別に認可ロジックを実装すればよく、Supabase AuthのRLSモデルに無理に当てはめる必要がない。

### 2.2 No.78／79：認証基盤の方式と3系統の分離【決定・9/30改訂】

データモデル設計の `accounts` は `password_hash` 列を持ち、認証を自前で実装する前提となっている。

**決定：** 利用者（`accounts`）および相談員・管理者（`counselors`）はSupabase Authを採用する。`accounts.password_hash` は廃止し、`accounts.account_id` は `auth.users.id` と対応させる。RLSポリシーは `auth.uid()` を起点に `accounts.client_id` へ到達させ、データモデル 0.2 のスコープを実現する。

**【9/30改訂】クライアント管理者（`client_admins`）も、`accounts`/`counselors`と同様にSupabase Authを採用する。** 当初（9/7時点）は自前実装の認証（別テーブル・別セッション）とする方針だったが、以下の理由により方針転換した。

- 自前実装はSupabase Auth標準のMFA・レート制限・パスワードポリシーを再実装することになり、対象人数の少なさに見合わないオーバーエンジニアリングと判断した
- 認証基盤そのものを分けなくても、**アクセス可能なデータの範囲をRLSで限定する**ことで7.6.1の分離の実質は担保できる：`client_admins`に紐づくロールは`cases`・`messages`等の相談内容系テーブルへの参照経路を持たず、事前集計済みのビュー（7.6.3の四半期レポート等）のみを参照できる

- `client_admins.admin_id` を `auth.users.id` に対応させ、`password_hash` 列は持たない
- ログイン・セッション発行はSupabase Authに委ね、自前のCookie・署名鍵は用いない
- パスワードポリシー・試行回数制限（No.75、76）・MFA（No.30）はSupabase Auth側の設定機能をそのまま用いる

**残る確認事項：** 7.6.1の「認証基盤を共有しない」を「ログインで越境できない・データ参照範囲が分離されていること」と読むなら本方式で満たせるが、「基盤そのものが物理的・論理的に別であること」まで求める趣旨であれば厳密には満たさない。自治体委託等の契約でこの点が具体的に問われた場合に改めて対応する（5.1.1のトリガー方式に準じる）。

この方式により、Supabaseプロジェクトを増やさずに認証基盤の分離という要件上の要求を満たせる。No.84（環境分離、単一インスタンス継続）とも整合する。

関連して、以下の既存項目の判断が本項に従属する。

- No.30（クライアント管理者の多要素認証の方式）：【9/30】Supabase Auth標準のTOTP（認証アプリ）を用いる。自前実装はしない
- No.75（認証の試行回数の上限とロックの期間）：【9/30決定・暫定】当面はSupabase Auth標準の接続元IP単位の回数制限のみとする。詳細は第4章 No.75 および 2.10 参照
- No.76（パスワードの最低文字数）：【9/30決定】8文字（3系統共通）
- No.11（既存の基本相談サービスとのアカウント連携）：既存のハッシュ形式によってはSupabase Authへの移行に制約が生じ得る

### 2.3 No.80：定期処理の実行基盤

データモデル 第9章に日次5種、月次1種、四半期1種の処理が定義されている。Vercelは常駐プロセスを持たないため、実行手段の決定を要する。

| 方式 | 適する処理 |
|---|---|
| Supabase `pg_cron` | DB内で完結する処理（猶予期間経過後の物理削除、集計） |
| Vercel Cron Jobs | 通知メールの送信を伴う処理（自動クローズの予告、同意の督促、有効期間満了の予告） |

**猶予期間を経過した本文の物理削除（9.3）は対象件数が事前に読めない。** サーバーレス関数の実行時間上限に抵触する可能性があるため、当該処理の方式は特に留意して決定する。

### 2.4 No.81：添付ファイル・画像の保管先

11.8.2の「別途調達を要するもの」にメール配信・決済代行・動画配信・LLMは挙げられているが、**添付ファイルの保管先が欠落している。** 該当するのは以下である。

| 対象 | データモデル上の列 | 性質 |
|---|---|---|
| 相談の添付ファイル | `attachments.file_ref` | 要配慮個人情報を含み得る |
| クライアントのロゴ画像 | `landing_pages.logo_ref` | 公開情報 |

前者は動画配信サービスやCDNとは別の扱いを要する。Supabase Storage を用いる場合はRLSと同等のアクセス制御設定を、外部サービスを用いる場合は国内保管要件（8.7）との整合を確認する。あわせて、9.3に定める物理削除の対象に添付ファイルの実体を含める手順を定める。

### 2.5 No.82：経緯サマリの一時保持先と生成タイミング

データモデル 3 の注記は、経緯サマリを保持せず「参照時に確定済みの `case_summaries` から都度生成する」と定めている。この記述をそのまま実装した場合、**案件詳細画面を開くたびにLLMを呼び出すこととなり、相談員の待ち時間が生じる。**

同注記が認めている「入力となる案件サマリの集合から算出した値を鍵とした一時保持」について、以下を確定する。

- 保持先（DBのテーブルとするか、別のキャッシュ機構とするか）
- 鍵の算出方法および失効の条件

本項は No.71（経緯サマリの入力とする案件件数の上限）と一体の問題であり、あわせて確定する。

### 2.6 No.83：2系統ドメインの出し分け

8.6.1は一般向けと企業会員向けを単一のアプリケーションで提供すると定めるが、実現方式は記載がない。**No.89の決定により、これはNuxtのミドルウェアによるホスト名判定ではなく、Vercelプロジェクト自体を分けたうえでのドメイン割り当てで実現する。** 相談者側アプリに一般向け・企業会員向けの両ドメインを割り当て、アプリ内部で契約類型に応じた出し分けを行う。

確定すべきは、8.6.1.1に定める「要素自体を設けない」という要件をアプリ内部の出し分けでどう担保するかである。決済に関する表示、機能1への投稿導線、会員区分の表示について、**非表示とするのではなく描画対象から除外する**構成とする必要がある。

### 2.7 No.84：環境分離とテストデータ【決定】

**決定：** 本番・ステージング用にSupabaseプロジェクトを追加することによる分離は、追加費用が生じるため現時点では行わない。Vercel・Supabaseとも単一インスタンスのまま開発を進める。将来、コストが許容できる段階で見直す。

単一インスタンスであることを前提に、以下を最低限の緩和策として実施する。

- **ローカル開発はSupabase CLI＋Dockerのローカル環境を用いる。** 追加費用なく、開発者の手元で完結する環境を作れる。これにより開発中のコードが本番DBに触れる経路をまず一つ塞げる
- **Vercelのプレビュー環境（プルリクエストごとに自動生成）には、サービスロールキーを配置しない。** 接続先は単一インスタンス（本番）にならざるを得ないが、anonキー＋RLS経由でのアクセスに限定し、RLSを迂回できる状態を作らない
- **サービスロールキーはProduction環境変数にのみ置く。** Preview・Developmentのスコープには含めない
- 合成データの生成・投入は、本番と同一インスタンス上で行わざるを得ないため、**本番の相談内容をコピーしての動作確認は行わない**運用ルールを明文化する
- 将来、追加費用を許容してプロジェクトを分離する際の移行手順（スキーマ・RLSポリシーの再現方法）を、着手前に一度整理しておくと切替がしやすい

なお、No.78/79（9/30改訂）により3系統とも同一のSupabase Authを用いるため、本項の単一インスタンス継続と整合している。

### 2.8 No.88：相談者数増大時のスケール手段【決定】

**決定：** 特定の手段に決め打たない。負荷の実態が出た時点で、その時点のボトルネックに応じて以下から選ぶ。現行設計（No.77のサーバールート経由、No.84の単一インスタンス、8.6.1のSSR）は、どの手段を選ぶ場合にも変更を要しない。

| 手段 | 何に効くか |
|---|---|
| Vercel側でのレート制限 | 突発的なアクセス集中・悪意あるリクエスト。No.77で全アクセスがサーバールートを通るため、ミドルウェアの追加のみで対応できる |
| Supabase接続プーラー（Supavisor）でのロール別接続数上限 | 相談者側の接続がDBの接続枠を食い潰す事態 |
| Supabaseのコンピュートスペックの引き上げ | 全体的な処理能力不足。インフラ側の設定変更のみ |
| リードレプリカの追加 | 機能1（Q&A閲覧）のような読み取りが多い処理 |
| Vercelのキャッシュ／ISR | 機能1のようなSSR前提の公開ページ |

**今のうちに意識しておくとよい点：** 機能1（読み取り中心）と機能2（書き込み中心・厳密な整合性が必要）は性質が異なる。DBへの問い合わせを書く際、「これは読み取り専用の処理か」を意識したコードの書き方にしておくと、将来リードレプリカを導入する際に該当箇所を探す手間が減る。今すぐの実装対応は不要で、コーディング時の習慣の話である。

### 2.9 No.89：Vercelアプリの分割範囲【決定・一部未確定】

**決定：** Vercelアプリ（Nuxt）を、相談者側（一般向け・企業会員向け、8.6.1）と管理側（運営の相談員・管理者）で分割する。理由は運用上の可用性ではなく、**セキュリティの被害範囲の限定**である。

- 相談者側は匿名・軽い認証のトラフィックを受け、攻撃対象になりやすい
- 管理側は少人数の相談員・管理者が使い、`緊急フラグ`対応という停止してはならない機能を持つ
- 単一アプリでは、相談者側の脆弱性が同一デプロイ内の管理側の環境変数・コードに到達し得る。分割すればアプリ層はその経路を断てる

**限界：** Supabaseは単一インスタンス（No.84）のままのため、DB接続・CPU・IOの競合はアプリを分けても解消しない。相談者側の負荷がDBを詰まらせれば、管理側のクエリにも影響する。この経路への緩和策はNo.88の接続プーラーでのロール分離を参照

**費用への影響：** Vercelの課金はチームのシート数と使用量（帯域・関数実行数等）が基準であり、プロジェクト数自体には課金されない。No.84のSupabaseプロジェクト分割（DBインスタンス増加分のコストが生じるため見送り）とは事情が異なり、追加費用なく実施できる

**実装方法：** Nuxt LayersまたはCommon packageで共通部分（Supabaseクライアント初期化、共通コンポーネント）を切り出し、2つのNuxtアプリ（2つのVercelプロジェクト）からそれぞれ参照する。環境変数は両プロジェクトに同一の値を設定する

**未確定：** クライアント管理サイト（7.6）をこの2分割のどちらに含めるか、あるいは3つ目のアプリとするかは未確定。クライアント管理者は相談内容系テーブルへの参照経路をRLSで持たず（No.78/79、9/30改訂）、扱うデータも事前集計値のみ（7.6.3）という低リスクな性質のため、さしあたり管理側に含める前提で進めてよいと考えるが、要確認

### 2.10 No.90：認証要件のうちSupabaseの上位プランに依存する機能【9/30判明】
