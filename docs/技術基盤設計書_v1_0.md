## 1. システム構成

### 1.1 全体構成

| レイヤー | 採用サービス | 備考 |
|---|---|---|
| ホスティング・コンピュート | Vercel | Nuxtアプリのデプロイ先。関数のリージョンは東京（`hnd1`）を明示指定する（既定は米国`iad1`） |
| データベース・認証・ストレージ・リアルタイム | Supabase（PostgreSQL） | プロジェクトリージョンは東京（`ap-northeast-1`）。単一インスタンスで運用（1.6参照） |
| アプリケーションフレームワーク | Nuxt（Vue） | 1.2のとおり2アプリに分割 |

### 1.2 アプリケーション分割

Nuxtアプリケーションを、対象とする利用者のリスク特性に応じて2つに分割し、それぞれ別のVercelプロジェクトとしてデプロイする。

| アプリ | 対象ドメイン | 利用者 |
|---|---|---|
| **相談者側アプリ** | 一般向けドメイン、企業会員向け`corp.`サブドメイン | 一般利用者、企業会員（匿名・軽い認証を含む、公開トラフィック） |
| **管理側アプリ** | 運営管理用ドメイン | 相談員・運営管理者（少人数、要MFA） |

**分割の理由：** 運用上の可用性ではなく、セキュリティ上の被害範囲の限定を目的とする。相談者側は攻撃対象になりやすい公開トラフィックを受ける一方、管理側は緊急フラグへの対応という停止してはならない機能を持つ。単一アプリの場合、相談者側の脆弱性が同一デプロイ内の管理側の環境変数・コードに到達し得るため、アプリ層を分離してこの経路を断つ。

**分割の限界：** Supabaseは単一インスタンス（1.6）であるため、DB接続・CPU・IOの競合はアプリを分けても解消しない。この経路への緩和はSupabase接続プーラーでのロール別接続数制御による（4章参照）。

**費用：** Vercelの課金はチームのシート数と使用量が基準であり、プロジェクト数には課金されない。分割による追加費用は生じない。

**実装方法：** 共通部分（Supabaseクライアント初期化、共通UIコンポーネント、型定義）はNuxt Layersまたは共通パッケージとして切り出し、2アプリから参照する。環境変数は両プロジェクトに同一の値を設定する。

**未確定：** クライアント管理サイト（要件定義書 7.6）をどちらのアプリに含めるかは未確定。クライアント管理者は3.2のとおり独自の認証を持ち、扱うデータも事前集計値のみ（7.6.3）という低リスクな性質のため、本書では暫定的に管理側アプリに含める前提とする。

### 1.3 リージョンと通信経路の整理

Vercel・SupabaseともCDN／PoP（受け渡し窓口）は世界中に分散するが、実際にデータを処理・保存する層（コンピュート・DB）は指定したリージョンに固定される。PoPはTLSを終端せず、暗号化されたまま最寄りのコンピュート層へ転送するため、本文が平文で経由することはない。

**Vercelを日本国内リージョン固定にするための具体策：**

- `vercel.json`で関数のリージョンを明示指定する（既定は米国`iad1`のため、指定しなければ処理は米国で行われる）
  ```json
  { "regions": ["hnd1"] }
  ```
  - Nuxt（Nitro）はビルド時にサーバー処理全体を1つの関数として出力するため、プロジェクト単位の`regions`で指定する。`functions`プロパティでソースのパス（`server/api/**`等）を指定する書き方は、該当する関数が見つからずデプロイエラーになるため使わない（9/30改訂）
  - Hobbyプランでも単一リージョンの指定は可能（複数リージョンはPro以上）
- **Edge Runtimeでは固定できない点に注意：** Edge Runtimeで実行される関数は、指定リージョンに関わらずクライアントの近接性に応じて実行場所がルーティングされる（真のリージョン固定にならない）。データを扱うサーバールートは、リージョン固定が保証されるNode.jsサーバーレスランタイム（既定）で実装し、Edge Runtimeを指定しない
  - Nuxtの `server/api/` はNode.jsランタイムが既定のため、明示的にEdgeへ切り替えない限りこの問題は生じない
- **実行リージョンの実測方法：** サーバールート内で`process.env.VERCEL_REGION`をログ出力・レスポンスに含めて確認できる。デプロイ後、意図したとおり`hnd1`で実行されているかを一度確認しておく
- 法務確認（9章）のためのDPA・サブプロセッサ一覧はVercel・Supabase双方の契約ページ上で参照する

## 2. 認証アーキテクチャ

### 2.1 3系統とも Supabase Auth に統一（改訂）

| 対象 | 認証方式 | 理由 |
|---|---|---|
| 利用者（`accounts`） | Supabase Auth | RLSポリシーで`auth.uid()`を直接利用できる |
| 相談員・運営管理者（`counselors`） | Supabase Auth | 同上。MFAはSupabase Auth標準機能を利用 |
| クライアント管理者（`client_admins`） | Supabase Auth | 2.3参照。自前実装から方針転換 |

### 2.2 データモデルへの反映

- `accounts.password_hash` は廃止し、`accounts.account_id` を `auth.users.id` に対応させる
- `counselors` も同様に `auth.users.id` に対応させる
- `client_admins` も同様に `password_hash` 列を廃止し、`client_admins.admin_id` を `auth.users.id` に対応させる。自前のセッションCookie・署名鍵は持たない

### 2.3 クライアント管理者の認証方式（改訂の経緯）

当初案は「Supabaseプロジェクトを分ける」ことで認証基盤を分離する方式、次いで「`client_admins`は自前実装のパスワード照合・セッション発行を行う」方式を検討したが、後者はオーバーエンジニアリングであり、かつSupabase Auth標準のMFA・レート制限・パスワードポリシーを自前で再実装するコストに見合わないとの判断から、最終的に以下の方式へ変更した。

- `client_admins`も`accounts`/`counselors`と同じ`auth.users`に登録し、ログイン・セッション発行はSupabase Authに委ねる
- 認証基盤そのものは分離しない。代わりに**アクセス可能なデータの範囲をRLSで限定する**ことで分離の実質を担保する：`client_admins`に紐づくロールは`cases`・`messages`等の相談内容系テーブルへの参照経路を持たず、事前集計済みのビュー（7.6.3の四半期レポート等）のみを参照できる
- パスワードポリシー・試行回数制限（要件定義書 No.75、76）・MFA（No.30）はSupabase Auth側の設定機能をそのまま用いる（自前実装しない）
  - 【9/30追記】ただし、試行回数制限のうち**アカウント単位の一時ロック**はSupabaseのTeamプラン以上でしか提供されず、Proプランでは設定だけでは実現できない。当面はIP単位の制限のみとし、本番投入前に方式を再決定する（2.4、未決事項一覧 No.75・No.90）

**確認事項（未解消のまま残す）：** 要件定義書7.6.1の「認証基盤を当社の管理画面と共有しない」を「ログインで越境できない・データ参照範囲が分離されていること」と読むなら本方式（同一`auth.users`＋RLSでのデータ分離）で満たせるが、「認証基盤そのものが物理的・論理的に別であること」まで求める趣旨であれば厳密には満たさない。自治体委託等の契約でこの点が具体的に問われた場合に改めて対応する（未決事項一覧 5.1.1のトリガー方式に準じる）。

### 2.4 認証の実装方針（9/30追記）

**設定値（Supabase Auth）**

| 項目 | 値 | 根拠 |
|---|---|---|
| パスワードの最低文字数 | 8文字。文字種の組合せは求めない | 要件 8.8.5、未決事項 No.76（9/30決定） |
| 多要素認証の方式 | TOTP（認証アプリ）。SMSは使わない | 要件 8.8.4（SMSは同居者による閲覧を防げない）、No.30 |
| 試行回数制限 | 当面はSupabase標準の接続元IP単位の制限のみ | No.75（9/30暫定決定） |
| メールアドレスの確認 | 有効（Confirm email） | 要件 8.4 |

**多要素認証の強制（運営側：要件 8.8.2「必須・例外なし」）は3層で行う**

1. 画面：管理側アプリの全画面ガード（`apps/admin/middleware/auth.global.ts`）。未ログイン→ログイン画面、MFA未通過（JWTの`aal`が`aal1`）→MFA画面、相談員として無効→権限なし画面
2. サーバーAPI：`apps/admin/server/utils/auth.ts` の `requireStaff()`。`aal2`であること、`counselors`に有効な行があることを毎回検査する
3. DB：`counselors`に有効な行を持つユーザーは、`aal2`のセッションでなければ相談内容系テーブル・`counselors`・`audit_logs`を1行も読めない（restrictive RLSポリシー、マイグレーション `staff_require_mfa`）。Realtimeの配信もこれに従う

管理側アプリはサーバー側でのHTML生成（SSR）を行わない（`ssr: false`）。全画面がログイン必須で検索エンジンの対象外であり、利用者の情報がサーバー生成のHTMLに混入する経路をなくすため。

**Supabaseの上位プランに依存する機能**（未決事項 No.90）

| 要件 | 必要なプラン | dev（Free）での扱い |
|---|---|---|
| 漏えいパスワードとの照合（8.8.5） | Pro以上 | 未確認。本番で有効化する |
| 無操作タイムアウト・セッション上限（10.4、8.8.2） | Pro以上 | 画面側・Cookie有効期間で代替（管理側は暫定8時間） |
| アカウント単位の一時ロック＋本人への通知（8.8.5） | Team以上 | 未実装（No.75） |

## 3. アクセス制御とセキュリティ

### 3.1 相談内容系テーブルへのアクセス経路

対象テーブル：`cases`、`messages`、`case_summaries`、`emergency_records`、`case_survey_answers`

**原則：** ブラウザからSupabaseのData API（PostgREST）を直接叩くことを認めない。これらのテーブルへの参照・更新は、例外なくNuxtのサーバールート経由とする。

**理由：** 要件定義書7.16は「相談内容へのアクセス（管理者による参照を含む）」を監査ログの重点監視対象と定めている。ブラウザから直接読む構成では、参照が発生した事実をアプリケーション側で記録できない。RLSはアクセスを制限する仕組みであり、参照を記録する仕組みではないため、この要件を満たせない。

**実装：** 当該サーバールートは、参照・更新のたびに`audit_logs`への記録を必須とする。

### 3.2 RLS（Row Level Security）の位置づけ

3.1の決定により、RLSは「唯一の防御」ではなく「サーバー側の実装ミスを受け止める多層防御の一枚」という位置づけになる。

**必須事項：** `cases`・`messages`・`case_summaries`・`emergency_records`にRLSを明示的に有効化する。Supabase Realtimeの配信はRLSポリシーに従って絞り込まれるため、有効化を怠ると当該テーブルにSELECT権限を持つロール全員に配信され得る。

**試験項目：** 実装初期に、相談員Aが相談員Bの案件を購読できないこと、個人利用者が他クライアントの行に到達できないことを確認する。

### 3.3 外部SNS連携との関係

要件定義書 No.5（外部SNS連携、LINE等）は導入する方針が決定している。実装時期は未定だが、外部IDと`accounts`を対応させるテーブルの器を先行して用意する。

3.1の決定（全アクセスがサーバールート経由）により、LINE等の外部経由の利用者が`auth.uid()`を持たない場合でも、サーバー側で個別に認可ロジックを実装すればよく、Supabase AuthのRLSモデルに無理に当てはめる必要はない。

### 3.4 テーブル権限（GRANT）の方針（9/30追記）

dev環境のSupabaseプロジェクトは「新しいテーブルをData APIに自動公開しない」設定で作成されており、テーブルを作っただけでは`anon`・`authenticated`・`service_role`のいずれにも読み書きの権限が付かない。RLSは「権限がある前提で行を絞る」仕組みのため、GRANTとRLSの両方がそろって初めてアクセスできる。この設定を活かし、権限は明示的に最小限だけ付与する（マイグレーション `explicit_grants`）。

| ロール | 付与する権限 | 理由 |
|---|---|---|
| `service_role` | 全テーブルの読み書き（今後作成するテーブルにも自動付与） | Nuxtのサーバールート（3.1）が使う。RLSは迂回するがGRANTは必要 |
| `authenticated` | RLSポリシーを設計済みのテーブルの**SELECTのみ**（相談内容系5テーブル、`accounts`、`counselors`、`client_admins`、`audit_logs`） | 相談内容系はRealtimeの購読（4章）にSELECT権限が必要なため。INSERT・UPDATE・DELETEは付与せず、書き込みは必ずサーバールート経由とする |
| `anon` | 付与しない | 未ログインで読めるデータは現時点でない。公開Q&A等は実装時に個別に付与する |

**新しいテーブルを追加するとき**：ブラウザから読ませる必要がなければ何もしなくてよい（`service_role`のみ自動で付く）。ブラウザから読ませる場合は、RLSポリシーとGRANTを同じマイグレーションで追加する。

本番用プロジェクトを作成する際も、同じ設定（自動公開しない）で作成し、本マイグレーションで権限をそろえること。

**RLSの試験**：`supabase/tests/rls_staff_isolation.sql`（3.2の試験項目を含むT1〜T8）。スキーマやポリシーを変更したら再実行する。

## 4. リアルタイム処理

要件から導かれる即時性の要求は一律ではない。以下のとおり区分する。

| 区分 | 対象 | 方式 |
|---|---|---|
| **必須** | 緊急フラグの通知（要件定義書 3.5、7.3、7.4）、ダッシュボードでの最上位固定表示（7.1） | Supabase Realtime による `cases.urgent_flag` の購読 |
| **望ましい** | メッセージの新着反映（7.3）、未処理件数バッジ（7.1）、稼働逼迫アラート（7.1） | Realtimeまたは定期ポーリング。数秒〜数十秒の遅延は許容。どちらを採るかは実装量と接続数の兼ね合いで判断する |
| **不要** | SLAタイマー・SLA残り時間の表示（7.2、7.3） | 起点時刻をサーバーから取得し、表示はクライアント側のタイマー計算による |
| **別論点** | 同時進行案件の排他制御（8.3）、決済Webhookの反映（8.3） | DBのトランザクション制御およびWebhook受信時の同期処理。リアルタイム配信とは別に実装する |

Supabase RealtimeのPostgres ChangesはRLSポリシーに従って配信対象を絞り込む。3.2の必須事項（RLS有効化）が、このリアルタイム層の安全性の前提となる。

## 5. 環境分離とデプロイ

### 5.1 構成

| 環境 | Vercel | Supabase |
|---|---|---|
| 本番 | Production | 単一プロジェクト（東京リージョン） |
| プレビュー | Preview（プルリクエストごとに自動生成） | 本番と同一プロジェクトに接続（5.2参照） |
| ローカル開発 | 各自のマシン | Supabase CLIでDocker上に起動 |

**決定：** 本番・ステージング用にSupabaseプロジェクトを追加する分離は、追加費用が生じるため現時点では行わない。単一インスタンスのまま運用する。

### 5.2 単一インスタンス運用における緩和策

- ローカル開発はSupabase CLI＋Dockerのローカル環境を用いる。開発中のコードが本番DBに触れる経路をまず一つ塞げる
- Vercelのプレビュー環境にはサービスロールキーを配置しない。anonキー＋RLS経由でのアクセスに限定し、RLSを迂回できる状態を作らない
- サービスロールキーはProduction環境変数にのみ置く
- 本番の相談内容をコピーしての動作確認は行わない。合成データの生成手順を別途整備する
- 将来、追加費用を許容してプロジェクトを分離する際の移行手順（スキーマ・RLSポリシーの再現方法）を、着手前に一度整理しておく

## 6. スケーラビリティ方針

相談者数の増大に対する具体的な手段は決め打たない。負荷の実態が出た時点で、その時点のボトルネックに応じて以下から選ぶ。本書で定めた設計（3.1のサーバールート経由、5章の単一インスタンス、要件定義書8.6.1のSSR）は、いずれの手段を選ぶ場合にも変更を要しない。

| 手段 | 何に効くか |
|---|---|
| Vercel側でのレート制限 | 突発的なアクセス集中・悪意あるリクエスト。3.1により全アクセスがサーバールートを通るため、ミドルウェアの追加のみで対応できる |
| Supabase接続プーラー（Supavisor）でのロール別接続数上限 | 相談者側の接続がDBの接続枠を食い潰す事態。1.2のアプリ分割では解消しない、DB層の競合への対処 |
| Supabaseのコンピュートスペックの引き上げ | 全体的な処理能力不足 |
| リードレプリカの追加 | 機能1（Q&A閲覧）のような読み取りが多い処理 |
| Vercelのキャッシュ／ISR | 機能1のようなSSR前提の公開ページ |

**実装上の推奨：** 機能1（読み取り中心）と機能2（書き込み中心・厳密な整合性が必要）は性質が異なる。DBへの問い合わせを書く際、読み取り専用の処理であることをコード上で判別しやすい書き方にしておくと、将来リードレプリカを導入する際の対応範囲を特定しやすい。

## 7. 定期処理

Vercelは常駐プロセスを持たないサーバーレス基盤のため、データモデル設計 第9章に定める定期処理は以下のいずれかで実行する。

| 方式 | 適する処理 |
|---|---|
| Supabase `pg_cron` | DB内で完結する処理（猶予期間経過後の物理削除、集計） |
| Vercel Cron Jobs | 通知メールの送信を伴う処理（自動クローズの予告、同意の督促、有効期間満了の予告） |

猶予期間を経過した本文の物理削除（9.3）は対象件数が事前に読めないため、サーバーレス関数の実行時間上限に抵触しない方式（`pg_cron`）を優先する。

## 8. 外部連携の受け皿

### 8.1 LLM（要件定義書 No.15）

初期実装ではインターフェースの枠のみ用意する。生成処理を1つのインターフェースの裏に隠し、エンドポイント・モデル名・APIキーは環境変数（Vercelの Sensitive 設定）で後から設定できる構成とする。

案件サマリはもともと相談員のレビューを経て確定する設計のため、下書きの出所を人からLLMへ差し替えるだけで移行できる。有効化は9章の保留事項のトリガー到達後とする。

### 8.2 添付ファイル・画像の保管先（未確定）

`attachments.file_ref`（相談の添付、要配慮個人情報を含み得る）と`landing_pages.logo_ref`（クライアントのロゴ、公開情報）の保管先は未確定（未決事項一覧 No.81）。相談の添付は動画配信・CDNとは別扱いとし、Supabase Storageを用いる場合はRLSと同等のアクセス制御を、外部サービスを用いる場合は9章の保留事項と同じ確認を要する。

## 9. 保留事項（法務確認待ち）

以下は代替手段の目処が立たないため現行構成のまま開発を進めるが、次のいずれかに到達した時点で必ず再確認する。

**トリガー：** ①要配慮個人情報（実際の相談内容）が本番環境に投入される前、②企業契約・自治体委託契約の締結前

**対象：**
- 基盤サービス（Vercel・Supabase）の選定と国内保管要件との整合
- LLMサービスの方式選定（8.1で有効化する際）

**確認の論点：** 「越境移転の同意が必要か」ではなく、Vercel・Supabase双方の契約条項が個人情報保護委員会Q&A 7-53の定める**クラウド例外**（クラウド事業者が個人データを取り扱わないこととなっている場合、第三者提供に該当しない）に該当するか、という形に絞り込み済み。トリガー到達時にはこの形で法務に依頼する。
